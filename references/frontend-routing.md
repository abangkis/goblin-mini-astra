# Frontend routing

Load before any frontend investigation, design, implementation, debugging, or visual/interaction testing. Only Sol and Astra frontend profiles in [model profiles](model-profiles.md) are allowed. This overrides general Scout/Routine/Deep routing, including small mechanical edits and FE scouting. Luna remains available for separable non-FE work.

Use the bounded frontend profile when design decisions are established; use frontend design and implementation for open UX decisions or complex UI work. Briefs such as "modern", "clean", or "premium" do not establish a design: identify open hierarchy, typography, spacing, composition, information density, responsive behavior, and interaction decisions. Existing components or an approved reference can establish those decisions; assess what remains open.

Keep work with a Sol Coordinator when its existing context makes direct execution efficient; small work does not require a separate worker or effort change. A Coordinator outside Sol/Astra can own scope and communication but must obtain frontend design, code, and visual acceptance evidence from an allowed profile. Never switch thread runtime silently. If no allowed route is available, report the limitation rather than falling back to Luna or another family.

Use frontend visual correction for a specific unresolved visual/interaction gap. Give it the brief, screenshots, observed gap, and bounded question; accept a targeted correction rather than restarting the frontend. For original visual direction, taste-led landing pages/portfolios/redesigns, or experience-wide tradeoffs, frontend original direction can be selected directly. Both Astra profiles require the core gate: unresolved question, why the current route is insufficient, needed evidence, and stopping condition. No failed Sol attempt is required.

For work where visual quality is a primary outcome, the design owner stays through the first rendered implementation and relevant interaction checks. Do not hand off only an abstract design description and assume quality survives implementation. A later mechanical remainder can go to an allowed bounded frontend profile when established decisions and handoff savings justify it. Integration and final task acceptance remain with the Coordinator.

Inspect rendered desktop/mobile screens and the primary interaction; code and passing builds alone do not establish visual quality. Reuse valid evidence and check new interactions after integration. Evaluate hierarchy, readability, consistency, responsive behavior, interaction completeness, and user acceptance.

Frontend work or task size alone does not justify escalation. Compare accepted results, user clarification, retries, handoffs, and attributable usage before claiming one profile improves quality or speed.
